# 洛璃服务：一个常驻进程，网页面板与 CLI 经它的接口使用助手

以前 CLI 和 Telegram 各是一个进程，各自把核心装进自己的进程里用。两个进程共用一个数据库，但互相看不到对方正在进行的回复。网页面板要实时显示正在进行的回复（「此刻」），也要能在网页里对话。用户希望以核心为中心，所有前端都经过它。

## 怎么做

- **一个常驻进程**：叫洛璃服务，由 `pnpm start` 启动。进程里有核心、Telegram 前端（设了 token 时才启动）和网页服务。只有这一个启动入口，`pnpm telegram` 去掉；再开一个带核心的进程，又会有互相看不见的回复。
- **核心仍是进程内的库**：不含网络、HTTP、登录这些事。`src/core` 不引用服务和网页的代码，由 lint 规则保证。核心的测试照旧用 mock 模型。
- **服务管理会话对象**：同一个会话在进程里只有一个会话对象，各前端都从服务取。
  - 回复的流经过服务时，服务旁听一份，转成实时事件：回复开始、思考、逐字输出、工具开始与结束、结束、出错、中止。
  - 服务记着每个进行中的回复当前到了哪里，网页新连上或重连时先发这份现场，再接着推。
- **对外的接口**：
  - 用 HTTP，只开一个端口，网页和 CLI 用同一套。
  - 对话接口输出 AI SDK 的 UI message stream。核心的回复本来就输出这种流，网页用 `useChat` 接。
  - 客户端每次只发新消息，会话的正本在服务端。会话管理里每个会话同时只有一个回复，所以生成中再发的消息由服务排队，当前回复结束后补一次回复，和 Telegram 的合并回复一样。
  - 图片单独上传：一条消息最多 10 张、每张 20 MB，放进 JSON 太大，所以上传接口的请求体是图片的原始字节，发消息时只带文件存储里的引用。
  - 实时事件走 SSE，需要的都是服务往外推。
- **框架用 Hono**：
  - AI SDK 的流式响应是标准的 Response，可以直接返回；
  - 客户端断开时，中止信号能传给核心；
  - 测试不用起端口，流式输出和中途断开都能测；
  - 网页能拿到接口的类型。
  - 写死版本、及时升级：近一年它在 cookie、防跨站、静态文件、SSE 这几块出过安全公告。
- **访问控制**：
  - 第六阶段只监听 `127.0.0.1`，不做登录。服务检查请求的来源（Origin、Host），只接受 JSON 请求体，挡住浏览器里其他网页发往本机的请求。
  - 唯一的例外是图片上传：只在上传接口、并且声明的是 PNG、JPEG、WebP、GIF 时收原始字节。这几种类型不在浏览器「简单请求」的类型之列，别的网页跨站发这种请求要先过预检，预检的 Origin 对不上，服务回 403、不给允许跨站的响应头，请求就发不出来；Origin、Host 的检查照旧。服务按内容核对格式，不只看声明的类型。
  - 第七阶段上公网时加登录，CLI 改为带 token 连接。
- **各前端怎么接**：
  - Telegram 前端留在服务进程里，直接使用服务管理的会话，不经 HTTP。
  - CLI 改为服务的客户端：通过接口发消息、收流式回复，「此刻」也看得到它的回复。服务没运行时提示后退出。`--model` 去掉，模型由服务统一配置。
  - 只读的导出脚本 `pnpm requests` 照旧单独运行。
- **代码位置**：
  - 服务的代码在 `src/server/`。
  - 网页在 `src/web/`：React 加 Motion，Vite 构建成静态文件，由服务提供。网页只能引用核心与服务的类型，不能引用它们的代码，因为浏览器里没有 Node。
  - 仍是单包。
- **网页自己的状态由服务管理**：比如未读数，存在服务端，不进核心的表。
- **退出**：不再接新连接和新消息；Telegram 的收尾和其余回复的宽限期同时等，最多 10 秒，到时没完的中止。网页会话的回复以中止结束，网页显示「已中止」，不是连接断开。

## Considered Options

- **网页服务单独一个进程，只读数据库**：看不到正在进行的回复，「此刻」只能显示写完的消息。
- **网页单独一个进程，和 bot 的进程之间另开通道传事件**：多一套进程间通信；两个进程里各有一个核心，仍然是两个洛璃。
- **把 HTTP 接口写进核心**：核心要感知网络和登录，「核心不引用平台代码」的规矩和核心的测试都要改。
- **Telegram 也作为客户端连服务**：多绕一层，没有好处。
- **CLI 保留独立运行的模式作为后备**：要维护两套路径。
- **CLI 走 Unix socket**：浏览器连不了 socket，网页仍要开端口；而且只能在本机用，服务部署到服务器后连不过去。
- **WebSocket**：需要的都是服务往外推。SSE 是普通的 HTTP，加登录、过反向代理都更简单。
- **Fastify**：
  - 官方插件齐全，但连同插件要多装六十来个包；
  - 带请求体的请求，读完请求体后中止信号就会触发，要自己绕过去。
- **只用 Node 自带的 http**：路由、静态文件、cookie、SSE、请求校验都要自己写。
- **多包（pnpm workspace）**：单包够用，以后要分开发布时再拆。
- **图片放进 JSON（base64）**：10 张 20 MB 的图片要几百 MB 的请求体，也就没法给对话接口设一个小的上限。
- **图片用 multipart 表单上传**：`multipart/form-data` 是「简单请求」的类型，别的网页不用过预检就能跨站发，只剩 Origin 检查挡着。

## Consequences

- 面板部署到哪里，bot 就跑在哪里；重启面板也会重启 bot。
- 服务进程停了，网页、CLI、Telegram 一起停。
- CLI 必须先启动服务才能用。
- 网页的依赖（React、Motion 等）进入仓库，多一步构建。
- 单用户：接口不区分用户。
