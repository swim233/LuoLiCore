# 每次发给模型的请求原样记下，存在单独的数据库里

发给模型的请求是每次临时拼出来的：人设与内置提示（每次从文件重读）、会话标题、之前的摘要、当前段的消息（工具结果按声明呈现）、工具定义、参数。以前发完就丢，出了问题只能凭日志里的时间推断模型当时收到了什么。起因是 Telegram 里换了人设后，模型仍自称旧身份，却看不到它当时实际收到的内容。现在核心把每一次实际发出的 HTTP 请求连同响应记下来，用于排查，也能拿出来原样重放。

## 记什么

- 每一次实际发出的请求都记一条：回复的每一步、摘要请求，以及请求阶段的重试、流中途的重试、图片被拒后换成占位的重试、失败的请求。每条注明会话、用途（回复、摘要）、回复 id、第几步、这一步的第几次尝试、开始时间、耗时、结果（completed、failed、aborted）。失败和重试正是排查时最想看的。
- 请求记实际发出的 HTTP 请求体，一字不差（Chat Completions 的 JSON）。SDK 转换格式时做的事都看得到：工具结果里的图片变成 `image_url`、收尾步不许调工具、system 的位置。在 provider 的 fetch 处截获，重试和失败的请求也就都在；请求头不记，API key 在请求头里。
- 响应记整理过的结果：状态码、输出的文字、思考内容（服务端返回时）、工具调用、结束原因、用量。失败时记错误体（抹掉 key）；流中途出错时，连同已经收到的半截。messages 表只存最后写进历史的版本，这些都不在里面。
- 只记实际发出的内容，不记用的是哪个人设文件。人设改一个字，记下的就是新的内容；之前的请求拼回来，仍是当时的样子。

## 怎么存

- 单独的 SQLite 文件，默认 `data/requests.db`（`LUOLI_REQUESTS_DB`），由核心存取，与 `data/luoli.db` 按会话 id、回复 id 对应。请求记录比对话本身大得多：每次请求都带着整段历史。分开存，主库保持小，这个文件删掉或清空也不影响对话。
- 按内容去重：请求体拆开，每条消息（system 也是一条）、整份工具定义各按内容的哈希存一份；每次请求只存引用列表和其余参数。同一段里后一次请求总带着前一次的全部消息，每次存完整请求体，体积随对话长度按平方增长；去重后只随新消息增长。拼回时字段顺序不变，与发出的一致。
- 请求里图片的 base64 解码后算 sha256，对上 `data/files/` 里的图（文件名就是内容的哈希）就只存 `luoli-file:` 引用；对不上的照原样存。
- 默认保留 30 天（`LUOLI_REQUEST_LOG_DAYS`，0 为永久）。启动时清理一次，之后每天一次：删掉超过期限的请求，再删掉剩下的请求都不再引用的内容。只动这个数据库；人设文件、`prompts/`、`data/files/`、`data/luoli.db` 一概不碰。
- 默认打开，`LUOLI_REQUEST_LOG=off` 关闭：问题往往发生过之后才想到要查，默认关着就查不到。写入出错只记日志，不影响回复。
- 内容和 messages 表一样是完整的对话，另外多了人设全文。它不是日志：`logs/luoli.log` 照旧不记正文。

## 导出

命令行脚本 `pnpm requests`，只读打开两个数据库，bot 运行时也能用。可以按会话（会话 id、Telegram 群 id 或群名里的几个字）、时间范围、回复 id 筛选，可以只看失败的；不给条件时导出最近 24 小时。输出一个 JSON 数组，一项一次请求：时间（本机时区）、会话（id、平台、标题）、用途、回复 id、第几步、第几次尝试、耗时、结果、完整的请求体、整理过的响应。图片默认写成引用，加参数才嵌回 base64，这时的请求体可以直接拿去重放。

## Considered Options

- 默认关、要排查时打开：问题往往已经发生过了。
- 用 SDK 在步结果里保留的请求体：只有成功的那一次。记 SDK 这一层的输入（ModelMessage）：看不到转换格式这一步。
- 只记拼装用的原料（人设版本、摘要、消息区间），需要时再拼：拼装逻辑一改，旧记录就拼不对了。
- 存进 `data/luoli.db`：主库膨胀，备份时只能连它一起带上。JSONL 文件：按会话筛要扫一遍所有文件，也难去重。
- 每次存完整的请求体，或整体压缩：体积仍按平方增长，压缩只缩小几倍。
- 图片照原样存 base64：与 `data/files/` 重复。
- 记原始响应流（SSE 的每一块）：体积大，几乎用不上。
- 永久保留：这份记录带着人设全文与完整对话，用途又只是排查近期的问题。按总大小清理：上限不好定，也说不清哪天的记录还在。
- 另外记下人设文件的路径：只在同时用好几个人设文件、又认不出某段人设出自哪个文件时才有用。
- 从数据库重建过去的请求：人设、内置提示、工具说明只能用现在的版本，拼不准的恰好是最想看的部分。
- 导出时按回复分组：筛选和重放都要多剥一层；平铺的每一项都带着回复 id，按它筛就行。

## Consequences

- 打开时多一个随对话增长的数据库文件，里面有保留期内的人设全文与完整对话。
- 超过保留期的请求查不到；只在那之前用过的人设版本也随之从记录里消失，人设文件本身不动。
- `data/files/` 里的图被删掉后，导出时嵌不回去，重放只能缺图。
- 每次请求多一次写库；写入失败的那次请求就缺记录，回复照常。
- 换用别的协议（如 Responses）时，请求体的格式随之改变，记录与导出照样可用。
