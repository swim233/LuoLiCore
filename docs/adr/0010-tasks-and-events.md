# 任务到点时在会话里写一条事件，当作一次触发

洛璃以前只在有人触发时开口。用户希望她在约好的时间也能说话，比如「明早 9 点提醒我交周报」「每天 8 点说说今天的天气」。这些任务都由洛璃在对话里建，到点时在原来的会话里开口。

## 怎么做

- **任务**：什么时候、在哪个会话、做什么。
  - 时间：
    - 一次性的定一个时刻，最远一年后。
    - 周期的只支持固定几种：每天、每个工作日、每周几、每月几号，再加一个时刻，可以设截止日期。
    - 按服务器的时区算。
  - 「做什么」：洛璃建任务时写的一句话，要能单独看懂。到点时会话可能已经切了段，当时的对话只剩摘要。
  - 来源：记下谁让建的（触发者），以及那条消息在平台上的 id。到点时的回复引用这条消息。
  - 状态：进行中、已完成、已取消。取消的任务不删。
  - 存储：
    - 任务存在 luoli.db 的任务表里，由核心的存储读写，表结构写进 ADR-0005。和会话、消息放在同一个文件里，一起备份。
    - 核心只存取任务，不调度，也不认识任务工具。
- **建任务**：洛璃在对话里用工具建，没有别的入口；面板只能看和取消。
  - 工具：
    - 一共四个：建任务、列出任务、取消任务，第八阶段加了改任务（ADR-0014）。
    - 只能看、只能取消、只能改本会话的任务。
    - 由服务提供，写成工厂函数，把定时器传进去，接在插件的工具后面一起装配。这和 ADR-0006 里平台工具的接法一样。
  - 白名单里谁都能建、能改、能取消。每个会话最多 20 个进行中的任务。
  - 会话：Telegram 的群和私聊、网页会话可以建。CLI 会话到点时多半没人看着，不能建。
  - system：现有的任务不放进 system。增删一个任务，后面整段前缀都要重算，缓存就失效了。要知道有哪些任务，洛璃调「列出任务」。
- **触发者**：这是 ADR-0006 留下的扩展点。`reply()` 带上可选的触发者，也就是触发这次回复的发言人，连同那条消息在平台上的 id；合并回复时可能有几个。触发者成为工具 `ctx` 的新字段。
- **到点**：定时器在洛璃服务里，常驻的进程只有它。
  - 它盯着最近的「下次到点」，启动时读一遍任务表，任务增删、改时间时重排。到点时先问会话所在平台的前端这个会话还收不收，不收的（如群被移出了白名单）把这次到点的任务取消，不写事件（ADR-0014）。
  - 到点时，它把事件交给会话所在的前端，当作一次触发。之后都走现有的路：
    - Telegram：照常等待合并；洛璃正在回复时被触发，就在这次回复之后补一次。回复引用任务的来源消息。
    - 网页会话：照对话接口的排队走；没有页面连着时，由服务读完回复。
    - 洛璃正在回别人时任务到点：回复排在它开始时看到的最后一条之后，所以事件排在这次回复后面。补的那次回复看得到事件。
- **事件**：会话里一条不是人说的消息，由服务写入。
  - 按用户消息存。AI SDK v7 不收历史里的 system 消息；放进助手消息里，又像是洛璃自己说的。
  - 事件没有发言人，metadata 的 `event` 里带类型和任务 id。
  - 送给模型时，格式化成 `<event type="task" task="t7" time="2026-11-10 09:00">任务到点：提醒小明交周报。小明在 11-09 21:30 让你建的，一次性任务。</event>`。
    - 格式说明里解释这个标签。
    - 事件的 `time` 和 `<message>` 的一样，可以当作现在的时间。
  - 事件存进历史，以后的回复和摘要都看得到。群里看不到；面板的时间线里显示成一行灰字；不算未读。
  - 类型用 `type` 区分。第七阶段有任务到点和错过两种；第八阶段加了监视查到了新的（`monitor`）和监视连续很久查不到（`monitor-failed`），见 ADR-0014；以后的后台任务也用这一套。
- **完成与错过**：
  - 一次性任务到点就算完成。之后的回复出错，照回复出错处理（Telegram 发那句固定的失败提示），不重做。
  - 周期任务到点后算出下一次，过了截止日期就算完成。
  - 服务停着时到点的任务不补。服务起来后写一条「任务超时」的事件，不触发回复；周期任务错过几次也只写一条，然后接着算下一次。有人问起时，洛璃知道错过了。

## 以后怎么接

监视、动态、插件是第八阶段的事，设计在 ADR-0014。和第七阶段拷问时的设想不同的有两处：

- 监视器不再是手写的代码模块。洛璃把一个监视写成一份描述，通用的引擎照着定时去查。
- 任务能改了：定时任务改时间和「做什么」，监视任务改间隔、条件、处理方式，不用取消再建。

还没做的：

- **推送地址（webhook）**：外部往服务的地址 POST，每次是一个事件。
  - 要等外网能访问才真正有用，所以和登录、密钥一起，在部署的阶段做。
  - 地址带着密钥，不在群里建。
- **后台长任务**：工具启动后立即返回，做完时写一条事件、发起一次回复，用的是同一套。还没有拷问过。
- **插件自己的存储**：等第一个需要它的插件来了再做。

## Considered Options

- 到点时直接发一句建任务时写好的话，不请求模型：能省一次调用，但这句话写于建任务时，看不到群里此刻的情况。周期任务（查天气、做总结）本来也要请求模型。
- 事件不存，回复时临时加在请求末尾：下一次回复时，洛璃不知道自己为什么说了那句话，摘要里也没有。
- 事件放进 system 或助手消息：v7 不收历史里的 system 消息；放进助手消息里，看起来像是洛璃自己说的。
- 现有任务的列表放进 system：每增删一次任务，前缀缓存就失效。
- 到点另开一条回复的路：Telegram 的等待合并、回复中被触发、网页的排队，都要重新处理一遍。
- 在面板里也能建、改任务：这和「在网页里改设置」是同一类事，留到那个阶段。
- 回复成功才算完成，失败了再到点一次：多一个状态，还要定重试几次。
- 错过的任务补一次（不管错过多久，或只补一小时内的）：隔了一夜再提醒已经晚了。用户选了只记一条事件。
- 周期写成 cron 表达式，或按间隔：要装解析库或者自己写，面板上还得翻译给人看。需要频繁去看的事，以后交给监视器。
- 只有用户本人能建任务，或者监视任务、周期任务只有用户本人能建：白名单里的人都可信，花费靠每个会话 20 个的上限管住。
- 第七阶段连监视器、插件、动态一起做：范围翻倍。用户想先用一段时间定时任务，再往下走。
- 任务存在服务自己的库里（像 `web.db`）：任务和会话、消息一样是长期数据，放在 luoli.db 里一起备份。服务照旧只经过核心存储的接口读写。

## Consequences

- 服务停着时到点的任务不会执行。服务跑在本机时，关机就会错过；部署到服务器之后才稳定。
- 每次到点都是一次模型调用。每个会话最多 20 个任务，周期任务最多一天到点一次。
- 群里的人看不到事件，只看到洛璃说的话。有人问「你为什么说这个」时，洛璃能从历史里找到原因。
- 改任务的时间，要取消再建（第八阶段起可以改，见 ADR-0014）。
