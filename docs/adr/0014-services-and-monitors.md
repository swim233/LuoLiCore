# 监视由洛璃写成描述，引擎照着定时去查；服务的文档和凭据由插件提供

第七阶段做了定时任务，洛璃只会在约好的时间开口。用户还想让她盯着外面的事：「上海有天气预警就说一声」。ADR-0010 的「以后怎么接」原来设想每个来源手写一个监视器模块。用户不要这种做法：加一个来源、改一下多久查一次都得改代码。用户要的是我们提供文档和环境，监视由洛璃在对话里自己写出来，以后还能在对话里改。

## 怎么做

- **插件**：仓库里的 `plugins/<名字>/` 目录，装一组相关的东西，清单（`plugins/index.ts`）里加一行就装上。
  - 一个插件里可以有代码工具（ADR-0006 的 `defineTool`），也可以有服务（声明加文档），加上它们要的环境变量。入口 `index.ts` 用 `definePlugin` 导出。
  - 插件在根包里，只许从一个专门的入口文件（`src/plugin-api.ts`）引东西，由 lint 规则保证。以后要单独打包，把这个入口换成包就行。
  - 只有洛璃服务引插件，而且只引清单；入口文件只给插件、清单和洛璃服务用。启动时由服务装配，插件名的规则同工具名，重名时报错退出。
  - fetch 搬过去，是第一个插件。核心照旧不引用插件。
- **服务**：洛璃能调用的一个外部接口提供方，由插件声明。
  - 声明里有：地址、认证方式、放行哪些接口、护栏、文档。只放行文档里写了的接口，只能读（GET）。
  - 凭据写在 `.env`，洛璃看不到。服务层把它贴在发往这个服务的请求上，发往别处的请求不贴。
  - 护栏是两个数：最短多久查一次、一天最多发多少次请求。洛璃一次性的查询和引擎的定时查询算在一起。到了上限当天不再发，第二天恢复。计数存在 `feeds.db` 里，重启后接着算。
  - 请求都走 fetch 那套防内网的做法：这段代码从 fetch 插件里搬到了 `src/net/`，两边共用。服务的请求不跟随跳转，凭据不会被带到别的地址。
  - 交给洛璃的正文和错误说明、日志里都抹掉凭据。
  - 缺环境变量的服务不装，启动时提示一行；环境变量都有但配置有误时启动报错退出。
  - 认证方式特殊的（要签名），在插件里写一小段代码；除此之外加一个服务不用写代码。
- **文档**：写给洛璃看的，分两层，她用到时用工具读，不放进 system（不影响前缀缓存）。
  - 服务文档：这个服务有哪些接口、参数怎么写、返回里有哪些字段、要注意什么。一个接口一节，可以只读一节。我们照官方文档写一份精简的。
  - 元文档：监视怎么写。描述有哪些字段、条件怎么写、先试跑再存。字段和条件的清单由引擎从校验规则里生成，指引和例子手写。
- **洛璃的工具**：都由洛璃服务提供，接在插件的工具后面一起装配。
  - 读文档；调服务（一次性的查询，如查天气、把城市名查成经纬度，不为它们另写工具）。
  - 监视的试跑、新建、修改、取消、列出。新建、修改、取消、列出就是任务的那四个工具（修改是 `update_task`）。
  - 查动态。
- **监视任务**：任务的第三种，和定时任务在同一张表里、面板上同一个列表。它没有约好的时刻，带着一份描述。
  - **描述**是洛璃写的一份数据，不是代码：
    - 服务、接口和参数；
    - 间隔，不能短于服务的最短间隔；
    - 条目在哪：返回里哪一段是列表；
    - 认新旧：哪个字段没见过才算新的；
    - 只要哪些：挑出值得到点的条目。条件有等于、不等于、是这几个值之一、大于小于、包含某个词，可以用「并且」「或者」和括号；
    - 给她看什么：到点时写进事件的字段；
    - 处理方式。
  - **试跑**：存之前，洛璃用工具让引擎照描述真的查一次，把取到几条、每条长什么样、哪几条符合条件给她看。建的时候程序自己还会再查一次，查不通就不建，所以存下来的描述都是查通过的。
  - 她直接建，不先问；建完说清楚建了什么。
  - 监视任务算进每个会话 20 个的上限，CLI 会话不能建。
- **引擎**：洛璃服务里的一部分，照描述定时去查，这一段不请求模型。
  - **来源**：服务、接口、参数、条目在哪、认新旧都相同就是同一个来源。请求只发一次，按盯着它的任务里最短的间隔；每个任务各自过滤、各自到点。没有任务盯着时停止查。
  - 每次：发请求，取出条目，没见过的存进动态，再按每个任务的条件过滤。没有要说的就结束。
  - 刚开始盯一个来源时查到的只存、不到点。之后一次查到几条，合成一个事件到点一次；一个事件里最多写 5 条的全文，其余只列标题，整条最多 6000 个字。
  - 「怎么把返回变成条目」是可以替换的一块，现在只有一种：JSON 里的一个列表。
  - 服务停着时不查。重启后查到的算新的，照常到点一次，不算「任务超时」。
  - 请求在排队之外发，一个服务慢不挡别的；处理结果和任务的建、改、取消、到点排成一串，不互相踩。引擎里出错只记日志，按查不到处理，不会马上再查。
- **动态**：查到的每一条都存下来，连同来源、时间、原始数据，去重也靠它。
  - 单独存一个文件（默认 `data/feeds.db`），由洛璃服务读写，启动时总是打开，默认一直保留。里面有来源（连同检查的状态）、动态、每个监视任务盯着哪个来源这三张表，加上每个服务每天的请求数。一条动态的原始数据最多存 64 KB。
  - 按来源存一份。任务取消后再建，以前的动态还在。
  - 动态和事件不在一个库里，不能一起提交。每个监视任务记着自己看到了哪一条（游标），先把事件写进会话，再推进游标：「动态存了、事件还没写服务就停了」的，重启后补写；「事件写了、游标还没推进就停了」的，重启后重一次，只重一次。
- **处理方式**：建监视任务时三选一，以后能改。只给监视任务，定时任务照旧都是触发回复。
  - 触发回复：写一条事件，当作一次触发，走第七阶段到点的那条路。
  - 只记录：写一条事件，不触发。
  - 洛璃自己决定：照常跑一次回复；她觉得不值得说，就只回一个约定的标记。
    - 这类回复整条攒到最后再发。最后是标记：群里什么都不发，这条回复不进历史。
    - 事件照常留在历史里。时间线里事件那一行照常显示，「此刻」里写「没有说话」，模型调用表照常记一行。
  - 到点的次数不设上限。
- **查不到**：网络不通、认证失败、额度用完。
  - 记下原因，拉长间隔再试：第 n 次连续失败后等「平时的间隔 × 2 的 n 次方」，最长一小时。认证失败（401、403）、被限流（429）、当天额度用完时直接一小时试一次，免得账号因为反复出错被冻结。
  - 返回的样子和描述对不上，也算查不到。任务所属的服务这次启动没装上（环境变量被拿掉了）：任务留着，不发请求，也算查不到。
  - 面板的任务行上标出「执行失败」，悬停看从什么时候起、最近一次的原因。
  - 连续失败满 6 小时，在会话里说一次（写一条事件、触发一次回复，不管处理方式是什么）。同一次故障只说一次，恢复以后不说。服务停过、电脑睡过以后不会马上误报：检查比排好的时间晚了超过 5 分钟又失败的，这一轮从那一次重新算。
- **修改**：监视任务和定时任务都能改，用同一个工具。
  - 定时任务能改时间和「做什么」。
  - 监视任务改服务、接口、参数、条目在哪、认新旧，就是换了来源：程序照新的描述重新查一次，查通了才生效，刚换时查到的只存不到点。改间隔、条件、给她看什么、处理方式、「做什么」，立刻生效。
  - 定时任务和监视任务不能互相改，要换就取消再建。
- **被移出白名单的群**：任务到点时发现群（私聊则是那个用户）已经不在白名单里，就把任务取消，不再每次写一条事件。
- **第一个服务是和风天气**（`plugins/qweather/`）：
  - 认证用 JWT（Ed25519 密钥对，私钥文件留在本机，Node 自带签名）。要配五个值：账号专属的主机名、开发者 ID、项目 ID、凭据 ID、私钥文件的路径。文档写着 2027 年起会限制 API KEY 每天的请求数。
  - 文档写四类接口：天气预警、城市查询、实时天气、逐天预报。预警、实时天气、逐天预报都只收经纬度（官方按经纬度查的新接口；按城市编号查的旧接口写着即将弃用），所以一般先调城市查询。
  - 最短间隔 5 分钟；每天最多 1500 次请求，数字在 `.env` 里能改。每月前 5 万次免费。
  - 建监视时洛璃先调城市查询，把经纬度和查到的地名写进描述；重名的把候选列给人挑。
  - 说预警时带一句来源，如「上海中心气象台发布，数据来自和风天气」。这是用这个接口的条件，写在服务文档里。
- **面板**：任务部件里监视任务的一行标出上次检查的时刻，能展开，看服务写成人话的几项（盯的是什么、参数、多久查一次、只要哪些、事件里写什么、处理方式）、上次检查的情况、到点过几次和描述原文；时间线里监视的两种事件能点开看正文；「此刻」标出这次回复是哪种事件触发的。写成人话的几项由服务算好，和工具结果里用的是同一套说法。不做单独的动态界面，也不能在面板上改描述。

## 以后怎么接

- **洛璃照着元文档给别的来源写监视**（用户说了后期想做）。要开的是环境，文档已经有了：
  - 公开地址：内置一个不带凭据的服务，走 fetch 的防内网请求；加上把 RSS、网页变成条目的转换，接在「怎么把返回变成条目」那一块上。描述的格式不用改，和环境绑定的只有「服务」这一个字段。
  - 新的带凭据的服务：她可以起草声明和文档，凭据只能由人放进 `.env`。
  - 放开以后她会读陌生网站的文档再照着建监视，被网页内容诱导的机会变大。那时每个地址的最短间隔、试跑、面板上看得到每条描述更要紧。
- **脚本**：描述写不出来的来源（要连调几个接口、要自己计算）再考虑让她写代码，那需要一个真的沙箱。
- **推送地址（webhook）、后台长任务、插件自己的存储**：照 ADR-0010 原来写的，没有变。

## Considered Options

- **每个来源手写一个监视器模块**（ADR-0010 原来的设想）：加来源、改间隔、改规则都要改代码。用户否了。
- **洛璃写脚本，在沙箱里定时跑**：什么都能做，但要一个真的沙箱（Node 自带的 `vm` 不是安全边界），写代码出错的方式多，面板上也只能显示一段代码。天气预警用不着。
- **每次检查都请求模型**（定时任务加工具）：不用写引擎，但没有新东西时也花一次带着整段对话的模型调用，10 分钟一次就是一天 144 次。
- **为查天气手写一个工具**：她读了文档能直接调接口，多一个工具只是多一份要维护的代码。
- **插件做成 workspace 里的包**，另建一个小包放定义函数：最接近「能单独打包」，但现在没有外面的人写插件，是提前花的功夫。
- **插件直接从核心引东西**：最省事，以后打包时每个插件都得改。
- **动态放进 luoli.db**：能和事件在一个事务里写；但原始数据越攒越多，会拖大对话那个库，而动态只有服务在用。
- **来源只按服务、接口、参数认**（拷问时的说法）：两个任务对同一个接口写了不同的「条目在哪」「认新旧」时，存下来的动态对不上。把这两项也算进来源。
- **建的时候只认「试跑过」**：要记住哪份描述试过，她试完又改了一点也拦不住。建的时候程序自己查一次更简单。
- **每个任务各查各的**：两个任务盯同一个地方就发两份请求；而且动态按来源只存一份，各查各的反而要另想办法让第二个任务不漏。
- **现成的表达式语言**：条件什么都能写，但要加依赖，她写错的机会也多，面板上没法一条一条显示。
- **建之前先问一声**：多一个来回，群里别人插话时容易乱。白名单里的人可信，护栏管住花费，试跑管住写错。
- **到点的次数设上限**：能防来源出毛病时多花模型调用。用户选了不设。
- **「洛璃自己决定」照常一步一步发**，只有一个字都没发出去时才算不说：发送的做法不用改。用户选了整条攒到最后再发，不会出现说了半截又决定不说的情况。
- **另起一次小的判断请求**（只给事件和一句标准）：便宜，但看不到群里刚才在聊什么。第七阶段的拷问里已经否了。
- **和风天气用 API KEY**：配置简单，但文档说 2027 年起限制每天的请求数。
- **每次查预警前重新查一遍城市**：什么都不存，请求数翻倍。**洛璃自己写经纬度**：不花请求，但坐标可能不准。
- **不放本地文档，让她用 fetch 读官方文档**：不用维护，但每次要抓好几页，慢，也容易读漏。

## Consequences

- 加一个来源不用改引擎：写一份文档、一份声明，配好凭据。认证方式特殊时才要写代码。
- 描述是洛璃写的，不在仓库里，没有测试守着。写错了靠试跑、面板和人在对话里纠正。
- 引擎只管一种情况：向配置好的服务发一个读请求，返回是 JSON，里面有一个列表，每条有能当 id 的字段。RSS、网页、要翻页的、「值变了」的都还做不了。
- 服务文档是我们照官方文档写的，官方改了要跟着改。老的预警接口 `/v7/warning/now` 就在 2026-10-01 停了。
- 间隔由洛璃定，花费靠护栏管；到点次数不设上限，来源出毛病时会多花模型调用。
- 「洛璃自己决定」的回复在调工具期间群里只看到「正在输入」，她先说的话要等到最后才出现。核心要多一个「这次回复不写入」的口子。
- 定时任务能改了，ADR-0010 里「改时间就取消再建」不再成立。
- 城市查询的结果记在描述里。和风的条款写着这个接口的数据不能缓存、批量存储；我们的理解是它管的是成批搬数据，一个任务记一个地点不算。
- 服务停着时不查，也不补；洛璃服务跑在本机时，关机期间发布又解除的预警她不会知道。
