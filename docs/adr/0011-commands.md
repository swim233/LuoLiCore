# 指令由各入口自己认，核心只提供压缩与清空两个操作

以前开始新的一段只有两种情况，都是自动的：空闲太久、上下文太长（ADR-0004）。用户想自己动手：话题换了，让洛璃把之前的忘掉；或者聊了很久，主动把之前的并成摘要。做法是在群里、在 CLI 里发一条指令：`/compact`、`/clear`。

## 怎么做

- **两个操作**：压缩和清空是会话对象上的两个操作，由核心提供。核心不认识指令的文字，`/compact`、`/clear` 这样的字符串不出现在核心里。
  - 压缩：当前段的全部消息连同之前的摘要并成新摘要，新开一段，新段从空开始。做法和空闲切段一样，不像自动压缩那样留最近 20 条原文。
    - 当前段没有消息时什么都不做。
    - 失败时不切段，上下文不变，也不影响自动压缩（不设失败后的那 10 分钟间隔）。
    - 可以中止，中止不算失败。
  - 清空：新开一段，不带摘要。助手从此看不到之前的原文和摘要。
    - 数据不删：消息、图片、请求记录都在，面板的时间线照旧能翻到。
    - system 里原来放摘要的位置写一句「更早的对话已在 2026-11-14 15:02 被清空」。文字来自 `prompts/cleared.md`，和别的提示词文件一样启动时检查、每次请求重读。之后再切段时，这句话照常交给摘要请求，由新摘要接替。
    - 当前段还没有消息、但带着摘要时（如空闲切段之后还没人说话），把这一段改成清空的段，不另开一段。既没有消息也没有摘要时什么都不做。
    - 这个会话的任务照旧保留，到点照常触发。
  - 界线：新的一段从调用那一刻最后一条消息的下一个序号开始。操作期间写入的消息归入新的一段；这时开始的回复先等操作结束，再读当前段。
  - 进行中的自动摘要（空闲切段、自动压缩）先中止，再做这一次：清空不需要它，压缩重新做一次，覆盖到最新的消息。
  - 执行人：谁在什么时候做的记在段上（显示名，平台有不变的 id 时连同 id），表结构见 ADR-0005。
  - 回复进行中调用，核心直接拒绝。「等这一轮回复结束」是各入口的事：一轮里有等待合并、补回复、排队，这些核心都不知道。
- **指令**：入口认出的一条文字。整条就是 `/compact` 或 `/clear` 才算，不分大小写，前后空白不算，不带参数；后面跟了字的当普通消息。
  - 指令消息不进会话历史，不触发回复，不算未读。
  - 每个入口各自认，各自排队，各自提示。只有两条指令，不做注册表、帮助、参数解析。
- **什么时候执行**：会话空着时马上执行；一轮回复还没结束时，等这一轮全部结束再执行。同一个会话的指令按先后一个个执行。两条指令一样，各入口一样。
- **Telegram**：
  - 白名单的群里谁都能用，私聊里白名单用户对自己的会话能用。`/clear` 不二次确认。
  - 可以带本 bot 的用户名（`/clear@nori_bot`）；带别的 bot 的用户名时当普通消息。写在图片说明里的、把旧消息编辑成指令的，都不算指令。别的以 `/` 开头的消息照旧当普通消息。
  - 发送时间早于 1 小时前的指令不执行，只记日志，和过期的触发同一个时限。
  - 提示是写在代码里的固定文字，引用指令那条消息发出，不进历史：「已清空上下文」「上下文已经是空的」「已压缩」「没有可压缩的内容」「压缩失败」「清空失败」。失败的详情只进日志。要等时不另外提示，执行完才回那一句。压缩期间显示「正在输入」。
  - 指令在后台执行：适配器按聊天排队处理消息，压缩要几十秒，不能占着这条队，期间群里的消息照常记录。
  - 指令菜单：bot 启动时登记这两条（默认范围），每次启动登记一次，失败只记日志。
  - 服务退出时：还在等的指令丢掉，进行中的压缩中止，不再发提示。
- **服务接口与 CLI**：
  - `POST /api/conversations/:id/compact`、`POST /api/conversations/:id/clear`，请求体带执行人的名字。只收 CLI 会话。
  - 响应是一串事件，和对话接口一样的流：要等时先发「等待」，轮到时发「开始」，最后发结果或出错。客户端断开就是取消：还在等的不执行，进行中的压缩中止。
  - CLI 里整行是指令才算，管道输入里同样认。提示写 stderr。等待和压缩期间按 Ctrl+C 取消。
- **面板**：只认得这两种段。时间线的分隔线写「清空 · 小明 · 11-14 15:02」「手动压缩 · 小明 · 11-14 15:02」。面板上没有压缩、清空的入口。

## Considered Options

- 清空时删掉数据：删了就找不回来，面板翻不到当时聊了什么，请求记录也对不上消息。清空只是让助手看不到。
- 清空后 system 里什么都不写：群友提到之前的事时，助手不知道有过更早的对话，容易顺着编。写一句话，她知道有过、但看不到。
- 手动压缩也留最近 20 条原文：自动压缩发生在聊到一半的时候，留原文是为了接得上；手动压缩是有人主动要重新开始，整段并进摘要更简单，和空闲切段是同一条路。
- 指令消息存进历史：模型会看到一条 `/clear`，对它没有用；清空的指令还会成为新一段的第一条消息。谁执行的记在段上就够了。
- 回复进行中收到指令，马上执行并中止回复：回复说到一半被自己人的指令打断，群里看着像出错。
- 回复进行中收到指令，拒绝并让人稍后再发：要人盯着回复结束再发一次。
- 排队做在核心里：一轮回复什么时候算结束，各入口不一样（Telegram 有等待合并和补回复，服务有排队的请求）。核心只保证「回复进行中不做」。
- 只让群管理员用、`/clear` 二次确认：白名单里都是自己人，数据也没删。用户定的。
- 通用的指令框架：只有两条指令，等有第三条再说。
- 做成工具，让洛璃自己压缩、清空：没有用例；她清空自己的上下文，后果比建一个任务大得多。
- 两个接口对 Telegram 会话、网页会话开放：Telegram 在群里发指令就行；网页没有入口，没有用例。
- 提示用模型生成：清空之后再请求一次模型来说「好的」，白花一次请求，而且这句回复该不该进新的一段也说不清。

## Consequences

- 清空没有撤销。指令登记在 Telegram 的菜单里，又不二次确认：在菜单里点一下 `/clear` 就执行了。数据都在，但没有「恢复」的入口。
- 登记菜单会覆盖在 BotFather 里设过的指令列表。
- 压缩、清空之后前缀变了，缓存失效一次。
- 指令不进历史，群里的人看得到那条 `/clear` 和提示，助手看不到；助手只从 system 的那句话知道被清空过。
- Telegram 在确认之前进程退出时会重发同一条更新，指令可能再执行一次：清空的第二次回「上下文已经是空的」。
- 服务退出时有回复正在等压缩：压缩马上中止，那次回复照退出的规则在宽限期内发出。群里看得到回复，看不到压缩的提示。
- 转发进群的一条 `/clear` 也算指令，执行人是转发的人。
- 「以调用那一刻为界」依赖存储的写入不让出执行权（现在的内存存储与 `node:sqlite` 都是同步的）。换成异步的存储、或两个进程写同一个库时，清空改写空段的那次重试可能把刚到的消息划到旧的一段里，到时要在存储里用一次事务完成。
