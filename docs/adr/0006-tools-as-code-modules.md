# 工具是仓库里的代码模块，由清单交给核心

一个工具一个文件（代码多时一个目录），放在 `src/tools/`，用核心提供的 `defineTool` 定义：名字、给模型看的说明、参数结构（zod）、需要的环境变量、超时、以后的回复里怎么呈现结果、执行函数。清单 `src/tools/index.ts` 列出要装的工具，前端启动时装配（检查名字与环境变量）后交给核心。核心只认这个形状，不认识具体工具，也不引用 `src/tools/`。加工具就是新建一个文件、在清单里加一行。

```ts
export const webSearch = defineTool({
  name: 'web_search',
  description: '搜索网页……什么时候用……',
  input: z.object({ query: z.string().describe('搜索词') }),
  env: ['LUOLI_TOOL_SEARCH_KEY'],
  timeoutMs: 30_000,
  history: { maxChars: 500 },
  execute: async ({ query }, ctx) => ({ results: [] }),
});
```

执行函数拿到的 `ctx` 是一个只往里加字段的对象：现在有会话 id 与名称、中止信号、日志、`env`。以后的能力都作为新字段加进来（见下文），已有的工具不用改。

回复用 `streamText` 的多步循环：模型调了工具，工具执行完，结果交回模型再请求一次。不用 `ToolLoopAgent`，它只是 `streamText` 的薄包装，却不支持流中途出错重试（`streamRetries`）。循环只设两道防失控的上限（步数、总时长），碰到时让模型用文字收尾；耗时长的工作以后交给异步任务。

工具出错或超时不让整次回复失败：这次调用以错误结果结束，模型看到错误说明，自己决定重试还是说明情况。

## 工具结果在历史里的样子

存储里永远是完整结果，当次回复的循环里模型看到的也是完整结果。以后的回复（和摘要）看到什么由工具声明：完整、不保留（只留调用和那次的回答）、截短到 N 字、或自定义的呈现函数；没声明的截短到统一上限。哪些结果值得留、留多少，写工具的人最清楚；统一上限兜底，忘了声明的工具也撑不爆上下文。呈现只由存下来的内容决定，同一条消息每次发给模型都一样，不破坏 ADR-0004 的前缀缓存。

回复中途结束（出错、超时、中止）时，已完成的步写入历史并加标记：群里已经看到的话、工具已经产生的副作用，模型以后应该知道。没有结果的工具调用补上「工具调用未完成」，否则下一次请求会被 SDK 拒绝。

## 工具的归属

通用工具（不依赖任何平台，如 fetch）放在 `src/tools/`，所有前端装同一份清单。核心不自带工具：核心是对话引擎，不因为某个工具多出网络请求、HTML 解析之类的依赖，去掉一个工具也不用动核心。

平台工具（发贴纸、置顶、查群成员……）放在前端目录（如 `src/telegram/tools/`），写成工厂函数：前端造工具时把平台对象（Chat SDK 的 thread、adapter）传进去，接在通用清单后面一起装配，交给核心。Telegram 前端为每个群建会话时可以按群造一份，工具执行时就知道作用在哪个群。核心不为平台工具加任何接口。各平台的操作差别很大，只有一个平台时先在核心抽一套通用接口，多半要返工；等真有了第二个平台、又有跨平台共用的平台工具，再考虑由核心定义平台操作的接口、前端提供实现。

## 工具结果里的图片

执行函数可以返回文字加图片，构造方式由核心提供，任何工具都能用（第一个用到的是 fetch：链接本身是图片时交给模型看）。图片存进文件存储，消息里只存 `luoli-file:` 引用，与用户发的图片一样（ADR-0005）。

当次回复里，图片放进 tool 消息交给模型：openai-compatible 打开 `supportsMultiPartToolContent`，tool 消息的内容变成文字加 `image_url` 部件。这不是 Chat Completions 的标准（标准里 tool 消息只能放文字），但用户的服务端实测可用，语义也最直接。以后的回复和摘要里，图片照样发，与用户发的图片一样。最初的设计是换成占位文字、要再看就再调一次工具，但实测时模型看到占位，以为自己当时没看过图，否认并推翻了自己正确的描述，也没有想到再调一次工具。保留的代价有限：每张图的 token 有上限（DeepSeek 每张最多约 1024），每次发出的内容相同，前缀缓存照常命中；摘要请求沿用回复的前缀（ADR-0004），同样带着图片。工具声明不保留结果时，图片一起省略。

某一步的请求因为本次回复工具结果里的图片被拒收时，把这些图片换成「[图片无法读取]」重试这一步，并把标记写进这条助手消息的 metadata，之后的请求都用占位。与用户图片的拒收不同的一处：重试仍失败时也写标记，否则这张图留在历史里、以后不再被当作可疑，服务端若真的读不了，之后每次回复都会被拒。已经被接受过的图片不算可疑：历史里的，以及本次回复里在更早的请求中发出过的。

## 以后怎么接

以下都还没做，等第一个需要它的工具来时再做。这里写明接法，保证现在的接口不会堵死它们。

- 触发者：第七阶段做了（ADR-0010）。`reply()` 带上可选的触发者（触发这次回复的发言人，连同那条消息在平台上的 id；合并回复时可能有几个），成为 `ctx` 的新字段。建任务时用它记下是谁让建的；以后的权限判断也以它为依据。
- 读本会话：`ctx` 加一个只读的会话视图（查历史消息、摘要），由核心按当前会话提供。
- 平台工具：接法见上文「工具的归属」。
- 权限与审批：用 SDK 的 `toolApproval`，在调用前按工具、触发者、会话判定允许或拒绝；拒绝时模型收到「被拒绝」的结果。需要有人点按的人工审批要跨请求续跑，群里新消息又会不断插进来，到时另议。
- 发到群里的文件：结果里的图片或文件已经存进文件存储；以后由回复流把它们交给前端，随回复发出。
- 图片放进 user 消息：换到只认标准写法的服务端时，图片改放在工具结果之后的一条 user 消息里（注明是工具取到的），核心在循环里和历史里都插这条消息。实测也可用。
- Responses 协议：它的工具结果原生支持图片，但用户现在的服务端没有这个接口；接 DeepSeek 等服务端时还要处理 `store` 与思考内容的回传。换服务端时另议。
- 子 agent：`ctx` 提供一次独立的模型调用（用当前模型，计入模型调用表）。
- 异步任务：定时任务第七阶段做了（ADR-0010）：到点时服务在会话里写一条事件，当作一次触发。监视器、后台长任务以后用同一套，见 ADR-0010 的「以后怎么接」。
- MCP：作为另一种工具来源，把 MCP server 的工具转成同样的定义。需要新依赖 `@ai-sdk/mcp`。

## Considered Options

- 启动时扫描 `src/tools/` 自动装上：只省清单里的一行，换来隐式的加载顺序与加载失败处理。
- 仓库外的插件目录，运行时加载：不改仓库就能加工具，但没有类型检查与测试，还要处理版本兼容。
- 只接 MCP：工具跑在别的进程里，要新依赖；以后可以作为一种来源接到同一个接口上。
- `ToolLoopAgent`：默认 20 步、配置集中，但没有 `streamRetries`。
- 历史里完整保留全部工具结果：上下文涨得快。只留回复文字：模型不知道自己调过什么，会重复查或说出没有依据的话。
- 按最近几次回复保留完整结果、更早的截短：每次回复都改写前面消息的样子，前缀缓存每轮失效。
- 中途失败照旧不写入：群里已发出的话和工具的副作用，模型以后都不知道。
- 工具出错时整次回复失败：网络、对方服务出错是常态，让模型处理更自然。
- 现在就做六个扩展点：每个扩展点的具体形状要等真正的工具才能定，现在做多半要返工。
- 核心自带一组通用工具：核心随工具一起变重，去掉一个工具也要改核心。
- 每个前端各写一份清单，从 `src/tools/` 里挑：没有「某个前端不装某个通用工具」的用例，只多了要同步的清单。
- 平台工具放 `src/tools/`，经 `ctx` 调核心定义的平台操作接口：同一个平台工具以后可以跨平台，测试时给假实现即可；但只有一个平台时接口定不准。
- 工具结果里的图片放进 user 消息：标准写法、换服务端也能用，但核心要在循环里和历史里都插消息；用户的服务端两种都可用，先用改动小的。
- 改走 Responses 协议：用户的服务端没有这个接口。
- 工具结果里的图片照默认转成文字：模型看到的是一长串 base64，认不出图，还占上下文。
- 以后的回复里图片换成占位文字：省 token，但实测模型会以为当时没看过图，推翻自己正确的描述。只保留最近几次回复的图片：每次回复都改写前面消息的样子，前缀缓存每轮失效。

## Consequences

- 加工具要改仓库代码并重启。
- 以后的回复里结果可能被截短或省略，模型要细节就得再查一次。
- 工具超时后核心不等它停下，它可能还在后台运行；有副作用的工具要正确响应中止信号。
- 中途失败的回复也会留在历史里（带标记），群里看到的和历史一致。
- 收尾步与摘要请求照旧发出工具定义、只是不许调用（`toolChoice: 'none'`），请求的前缀与回复一致。但有的服务端（如 DeepSeek）这时会把工具定义去掉，这两种请求就吃不到前缀缓存；它们都不常发生，影响有限。
- 工具结果带图片依赖服务端对 tool 消息的非标准扩展；换服务端前要先实测，不行就改走 user 消息。工具图片一直留在历史里，换到不收这种图片（或不能看图）的服务端时，历史里已有的图片会让请求被拒，这一点与用户发的图片相同。
- 回复期间群里的新消息要等这次回复结束后的下一次回复才看到。
