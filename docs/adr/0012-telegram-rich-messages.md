# Telegram 的回复用富文本消息发出，Markdown 由洛璃自己解析

洛璃在 Telegram 里的回复原来是纯文本：模型写的 `**加粗**`、列表、代码块都原样露着符号。用户又看到别的 bot 的消息正文下面有一条分隔线和一行小字，写着 token 用量，想给洛璃也加上。那种消息是 Bot API 10.1（2026-06）加的富文本消息（`sendRichMessage`）。这次一起做了四件事：回复改用富文本消息、正文按 Markdown 排版、最后一条的尾部显示用量、读懂别人发来的富文本消息。

## 怎么做

- **发送**：回复用 `sendRichMessage` 发，交给 Telegram 的是排好的块（`blocks`），Telegram 那边不再解析。
  - 引用、论坛话题、发送的时机都和以前一样。回复出错时那句固定的提示、指令（ADR-0011）的提示仍是普通消息。
  - 适配器（`@chat-adapter/telegram`）自己的 `postMessage` 只在消息是 Markdown 时才试富文本，转换的规则也不是我们的。我们在适配器的子类里直接调它的 `telegramFetch`。
- **Markdown**：洛璃自己解析，规则和网页面板一致：挨着中文标点的 `**` 照样加粗，一个回车就换行，不认「文字下面跟 `---`」的标题，原始 HTML 当文字，没闭合的写法原样显示。
  - 规则放在新的包 `@luoli/markdown`（`packages/markdown/`）里，面板和 Telegram 前端都按包名引用它。它只用 `marked` 的词法分析，给出词元；面板把词元画成 React 元素，Telegram 前端把词元转成块。
  - 词元转成块：段落、标题（1 到 6 级）、代码块（带语言）、列表（有序、无序、任务、嵌套）、引用、表格（表头、对齐）、分隔线、公式；行内的加粗、斜体、删除线、行内代码、链接、公式。
  - 链接只认 http、https，没写协议的域名补 https，别的协议当文字。图片不嵌进消息，显示成链接。直接写的网址、@用户名交给 Telegram 自己认。
  - Telegram 不收的写法（一个字都没有的标题、空的代码块）当段落，显示原文。
  - 写进会话历史的仍是洛璃的原文，面板、CLI、模型看到的都不变。
- **公式**：`$$…$$`、`\[…\]`、标成 `math` 的代码块是块公式；`\(…\)` 和加了限制的 `$…$` 是行内公式。内容原样交给 Telegram（LaTeX）。
  - `$…$` 的限制是为了不把钱数和 shell 变量认成公式：开头的 `$` 后面紧跟内容，结尾的 `$` 前面紧贴内容、后面不是数字，中间不换行。
  - 公式的识别是包的一个选项，只有 Telegram 前端打开。面板里公式仍是原样文字。
- **上限**：一条富文本消息的上限是在真的接口上试出来的：32768 个字、500 个块、16 层嵌套、表格 20 列。发之前自己数。
  - 字数按 JS 字符串的长度算。真接口对汉字、emoji 放得更宽，文档没写，不指望。
  - 块数连列表项、表格的行、里面的块都算。
  - 层数是每一处最里面的字外面一共套了几层。算一层的：引用；列表（连同列表项只算一层）；带字的块自己（段落、标题、代码块、表格，行和格子不算）；行内每一层样式、链接；`RichText` 的每一层数组。公式、分隔线自己不算。这个数法和真接口试出来的边界一致。
- **拆分**：字数、块数超了就在顶层的块之间拆成几条，每条都是富文本消息，每条都给尾部留了余量。不在块里面拆。超过 20 列的表格改成代码块，显示原文。
- **退路**：下面几种情况，这一条改发原文的普通消息（超过 4096 个字符照旧硬拆），别的几条照常发富文本。
  - 单独一个块自己就超限，或者嵌套超过 16 层；
  - Telegram 拒收这一条；
  - 服务端不认识这个接口（自己搭的旧 Bot API 服务端）：这次运行里之后都直接发普通消息。
  - 网络错误等别的失败照旧只记日志，不改发、不重试，这一步剩下的几条也不发。
- **尾部**：一次回复正常完成时，最后一条消息的下面写一行用量，如 `输入 5k · 缓存 4.1k · 输出 135 · 推理 102 · 3.2s`。
  - 是整次回复各步的合计。用时从开始生成算到回答写完，不含等待合并。
  - 富文本消息里是一条分隔线加一段下标小字；普通消息里是斜体的一行。
  - 出错的、被中止的、最后一步没有写字的回复没有尾部。尾部不写进会话历史。
  - 为了它，核心的用量多带了一项推理 token。
- **开关**：`LUOLI_TELEGRAM_RICH` 管发哪种消息、排不排 Markdown；`LUOLI_TELEGRAM_USAGE` 管尾部。不设时都打开，设成 `off` 关掉，各管各的。两个都关时和以前完全一样。
- **读收到的富文本消息**：别人发来的富文本消息转成 Markdown 文字记进历史，里面的唤醒词、@ 洛璃照样触发，被编辑时照样更新。
  - 字里本来就有的 `*`、`#` 等符号不转义：这段文字是给模型读的，面板和 CLI 对人发的消息又是原样显示，加了反斜杠到处都看得见。
  - 里面的照片和普通照片一样交给模型，一条消息最多看 10 张，文字里原来的位置留一个 `[图片]`。
  - 视频、音频、文件、地图、按钮记成占位文字。
  - 这是外面来的数据：每一处都先看类型，不对的当那一处没有。转换万一还是出错，这条消息记成「[不支持的消息]」，不会丢。
  - 面板和 CLI 不变：人发的消息照旧原样显示。
- **假的 Bot API**：测试里的假接口对富文本消息照真接口上试出来的规则收和拒收：认哪些块和字段、四个上限、层数的数法、空的标题和代码块、整条只有分隔线。真接口的行为变了，要回来改它。

## Considered Options

- 让 Telegram 解析（`sendRichMessage` 的 `markdown`、`html` 字段，或者普通消息的 `parse_mode`）：它的规则和面板不一样（中文旁的加粗、一个回车换行），同一段回复在两边排出来不同；写法不合它的规则时整条被拒收，也不知道错在哪。交块过去，上限和拆分都能自己数。
- 用适配器自带的富文本：传 Markdown 给 `postMessage` 它会自己试。转换规则、拆分、退路都不由我们定。
- 解析规则放在根包的一个中立目录里，不新建包：改动小，但面板（浏览器）和 Telegram 前端（Node）共用的代码没有清楚的边界。用户选了新建包。
- 尾部用 Telegram 自带的页脚块（`footer`）：真机上两种都发了样张，用户选了分隔线加下标小字。
- 按 UTF-8 字节数拆分：文档写的是「32768 个 UTF-8 字符」。真机上试出来是按字数，用户定了按字数。
- 满 4096 个字符硬拆（原来的做法）：会把一个代码块、一张表从中间拆开。
- 在块里面拆分（把一个超长的代码块拆成两个）：要处理每一种块怎么拆，超长的单个块很少见，直接走退路。
- 每一步各显示自己的用量，或者显示花了多少钱：尾部只写整次回复的合计，不记金额。
- 私聊里用 `sendRichMessageDraft` 逐字输出：只能用在私聊，群里用不了，先不做。
- 收到的富文本用适配器内部的转换函数：它没有导出，类型也比文档旧。
- 判断触发时另拼一份只有可见文字的（不带链接的网址、文件名）：现在这些也在转出来的文字里，唤醒词只出现在那里时也会触发，普通消息不会。少见，先不为它多做一套文字。

## Consequences

- 依赖 Bot API 10.1 以上的服务端。自己搭的旧服务端会自动退回普通消息，没有排版、尾部是斜体的一行。
- 依赖适配器 4.43.0 的几个内部方法（`telegramFetch`、拼聊天和引用参数的方法、错误类的名字），升级适配器前要核对。
- 面板和 Telegram 共用一套 Markdown 规则，改规则两边一起变。链接的规则有两份（组件库的 `linkHref` 和 Telegram 前端照它写的一份），要一起改。
- 字数按 JS 字符串的长度数，偏保守：汉字、emoji 多的长回复会比真接口允许的更早拆开。
- 很大的单个块（几百项的列表、几百行的表格、三万多字的一段）整块走退路，显示成原文。
- 公式写错了 Telegram 照收，显示成什么样由客户端决定。
- 模型不知道自己在 Telegram 里能用哪些格式（没有改提示词）。它写了 Telegram 排不了的东西时，显示成原样的字。
- 消息发出去以后不再编辑；尾部的写法、显示哪几项不能配置；开关不分群、不分人。
- 收到的富文本消息里第 11 张起的照片和交给了模型的照片一样写 `[图片]`，模型分不出哪几张没看到。
