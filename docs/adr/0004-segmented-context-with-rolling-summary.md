# 按段拼上下文，段之间用滚动摘要衔接

发给模型的内容固定为：system（人设、格式说明、会话标题、之前的摘要），之后是当前段的全部消息。一段之内新消息只往后追加，前缀不变，服务端的前缀缓存可以持续命中。

开始新的一段有两种情况：

- 空闲：会话超过 4 小时没有新消息。后台把旧摘要与刚结束的这段一起压缩成新摘要；程序重启后补做漏掉的。
- 压缩：上一轮请求的输入超过 300k token（按服务端报告的实际用量判断；回复有多步时看最后一步，各步之和会把同一段上下文重复计算）。较早的消息并入摘要，最近 20 条原文作为新段的开头。

摘要请求沿用当前对话的前缀，在末尾追加摘要指令。压缩发生在群里正在聊的时候，缓存还是热的，这次请求的输入大部分按缓存价计。

system 里越稳定的内容越靠前：人设与格式说明跨段不变，放在最前；会话标题与摘要每段变一次，放在后面。会话标题取段开始时的快照，一段之内改群名不影响前缀。每条消息自带的时间写在消息标签里，不放进 system。

system 各节与摘要指令的文字都来自文件（人设文件与仓库 `prompts/`），每次回复、每次摘要开始时重读，调提示词不用重启。文件不改时前缀照旧不变；改了文件，下一次请求的前缀跟着变，缓存失效一次，之后又能命中。

4 小时与缓存的有效期无关（服务端缓存通常几分钟到 1 小时就失效），它划分的是话题段落。段内缓存失效后，前缀没变，下一次请求重新写入缓存，之后又能命中。

## Considered Options

- 最近 N 条消息的滑动窗口：超出后每轮都丢最早一条，前缀每轮都变，缓存基本命中不了。
- 按 token 预算截断：同样每轮改变前缀。
- 全部历史：长度与花费无上限，迟早超出模型上限。
- 只靠空闲切段：活跃的群可能整天不空闲，上下文仍会无限变长。
- 只保留上一段的摘要：两段以前的内容会完全丢失。滚动摘要以固定长度带着最重要的事。
- 单独的摘要请求（专门的摘要说明加对话内容）：结果不受人设影响，但整段输入都按原价计。
- 提示词只在启动时读一次：一段之内前缀绝对不变，但每改一次提示词都要重启。

## Consequences

- 摘要请求带着人设，摘要指令必须写明用中性的第三人称、只记事实。
- 编辑一条消息会让缓存从这条消息往后失效，代价可以接受。
- 一段内图片原图一直留在历史里；压缩时与文字一起交给摘要请求。
